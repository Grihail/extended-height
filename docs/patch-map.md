# Patch map: всё, что в 1.7.10 зависит от высоты мира

Источник: декомпилированные исходники, которые выдаёт RetroFuturaGradle
(`build/rfg/minecraft-src`, Forge 1.7.10-10.13.4.1614, MCP stable_12). Список собран поиском по
коду, а не по памяти. Искал: `>> 4` в индексах массивов, `256`/`255`, `< 0`/`>= 0`/`> 0` рядом с y,
`getHeight()`/`getActualHeight()`, `storageArrays`/`getBlockStorageArray`, `-64`, `63`/`64`,
маски `1 << l` и `65535`, узкие типы (`readByte`/`readUnsignedByte`/`readShort`) в пакетах.
Цвета, звук, GUI и прочий шум отфильтрован вручную.

Статус: **веха 1 готова** (раздел «Статус вехи 1» в конце), остальное — план. Колонка «Риск» — насколько вероятно, что патч сломает
что-то или окажется неполным, а не насколько важен сам пункт.

## 0. Архитектурные решения, от которых зависят все патчи

| # | Решение | Почему |
| --- | --- | --- |
| 0.1 | **Внутри чанка y остаётся реальным.** `ExtendedBlockStorage.yBase` = реальный y (−256, −240, …). Смещение есть только в индексе массива: `index = (y >> 4) − minSection`. | Моды массово зовут `chunk.getBlock(x, worldY, z)` и `ebs.getYLocation()`. Сдвиг локальных координат в чанке сломал бы их все. `getYLocation()` уже реальный, поэтому сохранение и случайные тики работают без правок. |
| 0.2 | **Доступ к `Chunk.storageArrays[y >> 4]` патчится редиректами доступа к элементам массива** (`@Redirect(at = @At(value = "FIELD", args = "array=get"/"array=set"))`) с проверкой границ, причём только в методах, где индекс вычислен из y. Циклы `for l < storageArrays.length` не трогаются. | Это один механизм вместо `@Overwrite` десятка методов, и он меньше конфликтует с FastCraft и ArchaicFix. Для ванильного мира (`minSection = 0`, 16 секций) редирект — тождественная функция. |
| 0.3 | **Ограничения диапазона:** `minY ≤ 0`, `maxY ≥ 255`, обе границы кратны 16 (`maxY + 1` кратно 16), `minY ≥ −512`, число секций ≤ 64. Цель −256…319 = 36 секций. | Ванильный диапазон 0…255 всегда внутри мира, поэтому код, который проверяет «y в 0…255», ничего не ломает, а только недорабатывает. ≤ 64 секций — маска влезает в `long`. `minY ≥ −512` гарантирует, что сентинел `-999` в `precipitationHeightMap` и однобайтовый тег `Y` не пересекаются с реальными значениями. |
| 0.4 | **Ванильные миры = ванильный код.** Горячие пути (`World.getBlock`, `Chunk.getBlock`) правятся через `@ModifyConstant` (`256` → поле мира, `expandZeroConditions` для `y < 0`): для ванильного мира поле равно 256/0. Остальное — `@Inject(HEAD, cancellable)` с ранним `return` для нерасширенных миров. | Нет аллокаций `CallbackInfo` в горячих путях. Поведение ванильных миров доказуемо прежнее, это проверяет тест байтового сравнения сохранений. |
| 0.5 | **Где хранится диапазон:** в `level.dat`, тег `ExtendedHeight` (таблица dim → minY/maxY), через миксин в `WorldInfo`. Тег пишется, **только если есть хоть одно расширенное измерение.** Диапазон фиксируется в `World.<init>` сразу после `provider.registerWorld(this)` и до `createChunkProvider()`, то есть до первого чанка. | Ванильный `level.dat` не меняется. Измерение, у которого уже есть регион-файлы, но нет записи в таблице, навсегда остаётся ванильным: расширение не включится задним числом. |
| 0.5a | **Как определяется «у измерения уже есть сохранённые чанки».** Папка регионов: `<сохранение>/region` для измерения 0 и `<сохранение>/<WorldProvider.getSaveFolder()>/region` для остальных (например, `DIM-1/region`, `DIM4242/region`). Измерение считается существующим, если там есть хотя бы один файл `*.mca` (или старый `*.mcr`) ненулевого размера. Если `ISaveHandler` мира — не ванильный `SaveHandler` (папку не узнать), измерение остаётся ванильным: проверить нельзя, а гадать опасно. Код: `core/RangeResolver`. | Регион-файл появляется при первой записи чанка. До создания провайдера чанков он не открывается, поэтому проверка в `World.<init>` видит состояние диска до первого чанка. |
| 0.5b | **Что видит пользователь при поздней регистрации.** (1) `register(...)` вызван, когда измерение уже загружено: WARN `Height range for dimension N registered after the dimension was loaded; it takes effect only for dimensions created later.` (2) Расширение запрошено для измерения, у которого уже есть чанки без записи в `level.dat`: WARN `Dimension N: height range R requested, but the dimension already has saved chunks in <папка> and was created without the extension. It stays vanilla (0..255) forever.` (3) В `level.dat` сохранён один диапазон, запрошен другой: WARN, остаётся сохранённый. Во всех трёх случаях мир продолжает работать, краша нет. Новый диапазон записывается в `level.dat` **сразу** (`saveWorldInfo`), а не при следующем автосохранении. | Иначе сбой между первой записью чанков и первым сохранением `level.dat` дал бы измерение с расширенными чанками без записи о диапазоне. При следующем запуске оно открылось бы как ванильное. `saveWorldInfo` сохраняет и последний известный тег игрока, так что одиночная игра его не теряет. |
| 0.6 | **Опт-ин:** `ExtendedHeight.register(int dim, minY, maxY)`, `ExtendedHeight.register(WorldType, minY, maxY)` (только для dim 0) или интерфейс `IExtendedHeightProvider` на `WorldProvider`. | Вариант через `WorldType` нужен Reverworld. Вариант через интерфейс нужен модовым измерениям. |
| 0.7 | **Сеть:** мод обязателен на клиенте, если он есть на сервере (`@NetworkCheckHandler` с внятным сообщением). Клиент с модом может заходить на сервер без мода — тогда все миры ванильные. Пакеты в расширенном формате — **новые ID в `EnumConnectionState.PLAY`**. Они шлются только для расширенного мира и только если y вне 0…255. В остальных случаях летит ванильный пакет. | Новые ID обрабатываются в той же очереди, что и ванильные пакеты, поэтому порядок «чанк → изменение блока» сохраняется. У FML-каналов в 1.7.10 обработчики работают в netty-потоке, и порядок там не гарантирован. Ванильный сервер такие ID никогда не шлёт, поэтому клиент с модом его понимает. |
| 0.8 | **Сентинелы «ничего нет»:** пустая колонка `heightMap` = `minY` (в ванили 0), пустой чанк `getTopFilledSegment()` = `minY` (в ванили 0), «дождь некуда» = `minY` (в ванили −1), `getTopSolidOrLiquidBlock` «не нашли» = `minY − 1` (в ванили −1). | В расширенном мире 0 и −1 — настоящие координаты. Для ванильного мира все значения совпадают с прежними. |

### 5.A Лимит чанков в одном S26 (худший случай)

Худший случай для одной секции — все массивы заполнены несжимаемыми данными и есть небесный свет:
блоки 4096 + метаданные 2048 + блочный свет 2048 + небесный свет 2048 + `Add` (старшие биты ID) 2048 =
**12 288 байт**. Чанк из N секций плюс 256 байт биомов: `12288·N + 256`. Для 36 секций это **442 624 байта**.

Несжимаемые данные deflate не уменьшает, а немного увеличивает: zlib-заголовок 6 байт плюс 5 байт на каждый
«stored»-блок по 65 535 байт. Поэтому сжатый размер считается как верхняя граница
`deflateBound(n) = n + 5·⌈n / 65535⌉ + 6`. Кадр не может превышать 2 097 151 байт (21-битный varint длины).
Заголовок пакета: varint ID ≤ 3 + `short` число чанков + `int` длина + `byte` флаг неба + `byte` minSection.
На каждый чанк: `int` x + `int` z + `long` маска + `long` маска `Add` = 24 байта.

Правило: в пакет кладётся максимальное k, при котором `заголовок + 24·k + deflateBound(k · (12288·N + 256)) ≤ 2 097 151`.
Для N = 36 это **k = 4** (ваниль шлёт до 5). Для максимума N = 64 (786 688 байт на чанк) это k = 2. Один чанк
влезает при любом допустимом N, поэтому делить отправку одного чанка при текущих ограничениях не нужно. Если
ограничения когда-нибудь расширят, лимит считается той же формулой, а при k = 0 чанк уходит частями по секциям через
расширенный S21. **Тест:** собрать пакет из k чанков, где все секции и массивы `Add` заполнены случайными байтами,
сериализовать и проверить, что длина кадра ≤ 2 097 151, а для k + 1 — больше. Плюс round-trip: прочитанные данные
совпадают с исходными.

## Ошибка обфусцированной среды (найдена после вехи 2)

**Симптом:** собранный jar крашит настоящий клиент: `Critical injection failure: eh$resolveRange … (0/1) succeeded.
Scanned 0 target(s)`.

**Причина:** `@Inject(method = "<init>")` без дескриптора. У `World` два конструктора: общий
`(ISaveHandler, String, WorldSettings, WorldProvider, Profiler)` и клиентский `@SideOnly(CLIENT)`
`(ISaveHandler, String, WorldProvider, WorldSettings, Profiler)`. Annotation processor записал в refmap только
клиентский. В dev refmap не применяется, и `"<init>"` находил оба, поэтому все тесты проходили. В собранном jar
целью стал один клиентский конструктор: на сервере его вообще нет, а общий конструктор (миры сервера, в том числе
встроенного) инъекцию не получал.

Вторая половина причины видна только в обфусцированном клиенте. Forge разбил клиентский конструктор `World`: он
**не вызывает** `provider.registerWorld`. Этот вызов и `createChunkProvider()` перенесены в `finishSetup()`, его
вызывает `WorldClient`. Поэтому в клиентском конструкторе нет точки инъекции, отсюда `Scanned 0 target(s)`.

**Исправление:**

- общий конструктор (`WorldServer`) — `MixinWorld`, полный дескриптор;
- клиентские миры — `client/MixinWorldClientInit`: инъекция в `World.finishSetup` перед `createChunkProvider()`,
  то есть после `registerWorld` и после того, как Forge восстановит `provider.dimensionId`.

Оба с `require = allow = 1`. Заодно **все** 46 инжекторов мода получили точные `require = allow = N`: ни одно место
применения не может тихо пропасть или добавиться.

**Как это теперь ловится:** промежуточный вариант исправления (клиентский конструктор вместо `finishSetup`) упал в
`runObfClient` ровно с исходным сообщением, и фаза `obf client-audit` получила FAIL.

**Проверка остальных:** скрипт прошёл по refmap собранного jar и для каждого селектора без дескриптора посчитал
объявления с этим именем в декомпилированном целевом классе. Перегружен был только `World.<init>`. Методы Forge
(`getHeight`, `getActualHeight`, `canSnowAtBody`, `canBlockFreezeBody`, `getBlockLightOpacity`) помечены
`remap = false`: в рантайме у них нет SRG-имени. Окончательная проверка — прогон самотеста в обфусцированной среде.

## Чек-лист 3a, шаг 7 (выделенный сервер)

Пользователь проверить не может, проверено автоматически: фаза `net` в `scripts/selftest.ps1`. Выделенный сервер
(`runServer`/`runObfServer`, `level-type=extendedtest`, творческий режим, без защиты спавна) работает, пока к нему по TCP
на 127.0.0.1:25599 по очереди подключаются два настоящих клиента (`runClient`/`runObfClient`, отдельные JVM).
Подключение идёт тем же путём, что из списка серверов (`FMLClientHandler.connectToServer`).

- **Клиент с модом** (`selftest/NetClientSelfTest`, фаза `net-client`): шаги 2–4 чек-листа. Диапазон мира −256…319
  получен от сервера; каждый блок 3×3 чанков вокруг колонны на всём диапазоне совпадает с раскладкой генератора
  (слои, бедрок на −64, колонна до 319); правки сервера на y −100, 300, −50…−46 и −30 (расширенные S23, S22,
  частичный S21) дошли до клиента; игрок на y −100 и 300 жив, ломает и ставит блоки — результат подтверждает сервер.
  Клиент управляет сервером служебными строками чата `ehtest:…`, их обрабатывает только самотест
  (`selftest/NetServerSelfTest`). Пакеты здесь идут по настоящему проводу (без `forceWireRoundTrip`).
- **Клиент без мода** (фаза `net-nomod`): клиент убирает мод из списка модов FML-рукопожатия
  (`MixinHandshakeModList`, действует только в этой фазе) — сервер видит то же, что прислал бы клиент без мода.
  Сервер отказал, клиент показал: `This server requires the mod ExtendedHeight <версия> on the client (it changes
  the world height). Install it to join. (Mod rejections [FMLMod:extendedheight{…}])`.
- Сервер завершается сам, когда клиент с модом закончил и отказ клиенту без мода зафиксирован.

**Не проверено:** настоящий клиент без FML (ванильный) — его отключает сам FML с текстом «This is modded. No modded
response received»; несколько игроков одновременно; кадры, близкие к 2 МиБ.

## Шаг 5 плана Reverworld: эффекты пустоты мира (API)

`api/IVoidEffectsProvider` (на `WorldProvider` или `WorldType` для измерения 0) возвращает `api/VoidEffects`: туман

может только ослабить: `core/VoidEffectsResolver` — туман = выбор мира, `voidFog = off` его выключает, `on` включает
только в мирах без своего выбора; интенсивность = выбор мира × `voidParticleIntensity` (множитель ≤ 1). Без интерфейса —
встроенное поведение (без тумана, частицы ниже y 8, 50 %), при конфиге по умолчанию оно прежнее. Конфиг версии 2 с
переводом старых значений (`voidFog true/false` → `on/auto`, интенсивность 0.5 → множитель 1.0).

поведение ≈ половина от «полного» мира; мир без частиц — ни одной частицы при любом конфиге; мир с частицами у дна — ни
одной на y −100; множитель 0.5 — половина, 0 — ни одной; таблица тумана (мир вкл + auto = вкл, мир вкл + off = выкл,
мир выкл + on = выкл, встроенное + on = вкл, встроенное + auto = выкл); ванильный мир — без эффектов библиотеки.

`core/EhMath.yForIntCast`: в расширенном мире при y < 0 — `floor(y)`, иначе y как есть (ванильный мир — ванильный код).
Миксины — `mixins/early/ycast/*`, у каждого `require = allow = 1`.

## Статус вехи 2

**Подход.** Для расширенных чанков алгоритмы света заменены целиком: `@Inject(HEAD)` с отменой и та же логика с
реальным y и `minY` вместо 0. Ванильные чанки выходят из инъекции сразу и выполняют нетронутый ванильный код.
Точечная замена констант здесь не годится: в одних и тех же методах «y > 0» (дно мира) перемешано с «light > 0»
(уровень света), а ординалы нулей хрупкие.

| # | Где | Что сделано |
| --- | --- | --- |
| 3.1 | `MixinChunkLight`: `generateSkylightMap` | Заливка колонок и heightMap до `minY` |
| 3.2 | `client/MixinChunkClient`: `generateHeightMap` | То же для клиента (**не проверено**, веха 3) |
| 3.3 | `MixinChunkLight`: `relightBlock` | Без маски `& 255`, циклы до `minY` |
| 3.4 | `MixinChunkLight`: `func_150811_f` | Дно прохода — `minY`, эвристика уровня моря 63 оставлена |
| 1.9 | `MixinChunkLight`: `enqueueRelightChecks` | `sections × 256` проверок, y = `minY + 16·section + ly` |
| 3.8 | `MixinChunk.<init>` | heightMap пустых колонок = `minY`, `queuedLightChecks` = `sections × 256` |
| 2.7 | `client/MixinWorldClientLight`: `getSkyBlockTypeBrightness` | Константы 0/256 → границы мира (**не проверено**, веха 3) |
| 3.5–3.7 | `recheckGaps`, `updateLightByType`, `computeLightValue` | Без изменений: работают через heightMap и границы из вехи 1 |

**Проверено автоматически** (`scripts/selftest.ps1`: фаза write — 218 проверок, verify — 75). Четыре полных прогона
без FAIL; в первых трёх ещё не было проверки тиковых проходов (193 проверки в write). Каждая конструкция — полость из воздуха и источников света в каменной оболочке. После
каждого шага **все** ячейки полости сверяются по небесному и блочному свету с эталоном `LightReference`, оболочка
должна быть тёмной, heightMap всех задействованных колонок — совпадать с независимым сканированием колонки.

- **Эталон.** `LightReference` — перебор до неподвижной точки по правилу `World.computeLightValue`, без
  зависимостей от кода игры. Сам эталон покрыт 5 юнит-тестами.
- **Небесный свет через границы секций:** шахта, открытая сверху на `maxY` (319), от y −20, через границы 256 и 0.
  Боковой тоннель на y 0 со спуском до −4 (граница 0/−1) и тоннель на y 256 с вертикалью 252…260 (граница
  255/256). 362 ячейки.
- **Блочный свет:** глоустоун на y −200 в закрытом боксе через границу чанков x 15/16 (924 ячейки); затем источник
  убирается и ставится уже в соседнем чанке.
- **Пересчёт:** крышка на `maxY` ставится и убирается; тоннель на y 0 перекрывается и открывается; у дна мира
  (бокс на `minY`, 245 ячеек) источник на `minY` убирается и ставится на другой высоте, камень на `minY` ставится и
  убирается. Сверка идёт **сразу после `World.setBlock`, без принудительного пересчёта** — то есть проверяется
  штатный инкрементальный путь.
- **Свежепостроенные конструкции** совпадают с эталоном ещё до «досвечивания» (0 расхождений во всех трёх). Затем
  `updateLightByType` по всем ячейкам ничего не меняет за один проход.
- **Тиковые проходы** — полный круг `enqueueRelightChecks` и проход `func_150809_p` по всем чанкам конструкций — свет
  не портят.
- **heightMap и осадки:** пустая колонка (`minY`); блок на −200; блоки на −200 и `minY`; удаление блоков по одному;
  блок на `maxY` (heightMap 320, под ним небесный свет 14); блок на 0 и на −1. В каждом случае `getHeightValue`,
  `getPrecipitationHeight` и кэш `precipitationHeightMap` сверяются со сканированием колонки.
- **Сохранение и загрузка:** 1680 значений (свет всех ячеек и heightMap колонок) записаны до сохранения и
  совпадают после перезапуска. После перезапуска конструкции снова сверены с эталоном.

**Ванильная особенность, сохранённая намеренно.** Нижний ряд колонки не сканируется ни для осадков, ни для заливки
неба (в ванили — y = 0). Одиночный блок на `minY` даёт heightMap `minY + 1`, но высоту осадков «нет» (`minY`), как в
ванили одиночный блок на y 0 даёт −1.

**Не проверено:** клиентские методы (`generateHeightMap`, `getSkyBlockTypeBrightness`) — у клиента ещё нет
диапазона, это веха 3; измерения без неба (`hasNoSky`) в расширенном режиме.

**Производительность:** [perf.md](perf.md). Мод добавляет к `getBlock` в ванильном мире около 0,4 нс (5–10%).

**Уроки реализации, важные для следующих вех:**

- `require` в Mixin считается **суммарно по всем методам аннотации**. Каждая аннотация с несколькими целями
  указывает точное ожидаемое число инъекций (`require = allow = N`), иначе одна непримененная инъекция проходит
  молча. Именно так нашлась первая ошибка.
- Редирект записи в массив несовместим с цепочкой `a = arr[i] = new X(...)` (`DUP_X2` → VerifyError).
  `@ModifyVariable` на `LOAD` переписывает саму локальную переменную, а не одно загруженное значение. Для таких мест
  в `Chunk` (`func_150807_a`, `setLightValue`) секция в расширенном чанке создаётся заранее в `@Inject(HEAD)`.
- Во время `World.<init>` у `WorldServerMulti` поле `worldInfo` — временная копия `level.dat`; таблица диапазонов
  всегда берётся из `WorldInfo` измерения 0 (0.5b). Ошибка поймана самотестом: запись о диапазоне терялась при
  остановке сервера.
